## 2. 사고 A — 공표 수치 덮어쓰기

### 무슨 일이

2026-09-26 23:02~23:06 의 DR-trained 4-seed 측정이 `rollout_summary_rs232*.json` 4개를
**그대로 덮었다.** 이 파일들은 대시보드가 공표 수치를 읽는 원본이다.

결과: 9/26~10/02 사이 대시보드 공표값이
- `rollout_metrics.rs232` = **0.425 / 0.325** (목표 0.50 **미달** 표시)
- 동시에 `phases[phase4].outcome` 은 `build.py` 하드코딩이라 **"0.600 · 완료 기준 충족"** 유지

→ **한 화면에서 두 수치가 모순**된 상태로 6일간 노출됐다.

또한 사전 확정된 채택 규칙(`research/decisions/2026-09-24_dr-retrain-adoption-rule.md`)은
17/40 을 "헤드라인 유지 + 부록 병기" 밴드로 정해 뒀으므로, **공표 상태가 규칙과 어긋나 있었다.**

### 왜

측정기 `scripts/render_act_rollout_rs232.py` 의 출력 파일명에 데이터셋·체크포인트 구분자가 없었다.

2026-09-24 에 드라이버를 고치면서 체크포인트 디렉터리는 격리했다
(`episodes_rs232`→`act_rs232_sim` / `episodes_rs232_dr`→`act_rs232_dr_sim`).
**그런데 격리를 한 군데만 했다.** 측정 산출물 경로·영상 파일명·`ckpt_dir` 라벨·드라이버의
성공률 출처는 전부 공유인 채로 남았다. 공유 경로가 넷 있었고 그중 하나로 샜다.

### 복구

1. DR 결과 4건을 `rollout_summary_rs232_dr*.json` 으로 보존 (비교 arm 유지)
2. 공칭 4건을 git `d2f4c17` 에서 복구
   (`ckpt=act_rs232_sim/epoch_0041`, `measured_at=2026-09-18T23:02:14`)
3. 재빌드 검증: `partial 24/40 = 0.600 · full 24/40 = 0.600 · target 0.50 · 충족 True`

### 재발 차단 — 격리를 네 군데 전부

| 경로 | 조치 | 커밋 |
|---|---|---|
| 체크포인트 디렉터리 | `act_${DS_BASE#episodes_}_sim` | `7077a89` (9/24) |
| 측정 산출물 JSON | `VARIANT_TAG` 도입 — 공칭 `""` / DR `"_dr"` | `5168f22` |
| 추론 영상 파일명 | `RUN_TAG` 고정 → 실제 체크포인트 디렉터리명 | `5168f22` |
| summary 의 `ckpt_dir` 라벨 | `RUN_TAG` 고정 → 실제 디렉터리명 (DR 결과가 공칭으로 라벨되던 것) | `5168f22` |
| 드라이버 성공률 출처 | 전이 로그 grep → 측정 산출물 JSON | `6ebbb5d` |

마지막 항목은 마커 복원 뒤에도 남아 있던 구멍이다. `logs/cop_rollout.log` 는 **마지막 측정
실행의 stdout 캡처**일 뿐이라 다른 사이클 결과가 남는다. 실제로 마커를 공칭으로 되돌린 뒤에도
`데이터 episodes_rs232 … 최종 성공률=0.425` 가 출력됐고, 이 값은 야간 연구로그를 거쳐
대시보드로 들어가므로 오염 경로였다.

**로그 자체는 고쳐 쓰지 않았다.** 마지막 실행 기록을 바꾸는 것은 이력 날조다. 출처를 바꿨다.

검증:
```
episodes_rs232     → [0.6, 0.7, 0.6, 0.5] → 0.600  (act_rs232_sim)
episodes_rs232_dr  → [0.6, 0.5, 0.1, 0.5] → 0.425  (act_rs232_dr_sim)
```
두 변형의 파일 집합이 교차하지 않음을 확인했다.

## 3. 사고 B — 야간 문서화·커밋 계층 중단

### 무슨 일이

2026-09-28 부터 23:00·23:30 잡이 매일 실패했다.

```
Failed to authenticate. API Error: 401 OAuth access token has expired. Re-authenticate to continue.
```

`cop_common.py` 는 `--bare` 를 의도적으로 쓰지 않아 구독 OAuth 로 `claude -p` 를 호출한다.
자격증명은 macOS Keychain `Claude Code-credentials` 에 있고
(`~/.claude/.credentials.json` 없음, `.env` 의 `CLAUDE_CODE_OAUTH_TOKEN`·`ANTHROPIC_API_KEY` 는 공란),
비 GUI 컨텍스트에서 리프레시가 되지 않은 것으로 보인다.

### 중요 — 파이프라인은 멀쩡했다

실패한 것은 `claude -p` **이후** 단계(문서화·커밋·푸시)뿐이다.
`pipeline_advance` 는 매일 정상 수행됐고 `STAGE=완료/유지` 로 끝났다.
학습·측정·체크포인트·마커 어디에도 손상이 없다.

### 공백의 범위

| 날짜 | 연구로그 | 시뮬문서 | 일일보고 |
|---|---|---|---|
| 09-27 | ✅ | ✅ | ✅ |
| 09-28 ~ 10-02 | ❌ | ❌ | ❌ |

일일보고(07:00 잡)가 비어 있는 것은 **설계대로**다. `_check_upstream_failures()` 가
전날 23:00 잡 실패를 감지하면 가짜 보고서를 만들지 않고 조기 종료한다.
깨진 상류 위에 보고서를 세우지 않는다는 가드가 의도대로 작동했다.

### 복구

2026-10-02 사용자 재인증. 검증:
```
claude auth status → loggedIn: true, authMethod: claude.ai, subscriptionType: max
claude -p "숫자 7만 출력해" → 7 (exit 0)
```

**단, 이 검증은 대화형 셸 컨텍스트에서 수행됐다.** 크론 컨텍스트에서의 확증은
2026-10-02 23:00 잡이 `status: ok` 로 끝나는 것으로만 가능하다.
재발 시 권장 조치는 `claude setup-token` 으로 장수명 토큰을 발급해
`~/.hermes/.env` 의 `CLAUDE_CODE_OAUTH_TOKEN` 에 넣는 것이다 — Keychain 리프레시 경로를 타지 않는다.

## 4. 배운 것

1. **격리는 전부 하거나 안 한 것과 같다.** 체크포인트만 격리하고 산출물·로그를 공유로 두면
   공유 경로로 샌다. 9/24 패치는 경로 하나만 막았고 나머지 넷 중 하나로 사고가 났다.
2. **감사 계층이 죽으면 사고가 조용해진다.** 야간 에이전트는 매일 무결성 감사를 하도록 돼 있었고
   그 감사가 A 를 잡았을 것이다. B 가 A 를 6일간 가렸다.
3. **전이 파일을 권위 있는 출처로 쓰지 않는다.** `cop_rollout.log` 는 stdout 캡처이지 산출물이 아니다.
4. **실패를 알리는 경로가 실패와 같은 자격증명을 쓰면 무음이 된다.**
   메일 알림도 같은 기간 SMTP 535 로 죽어 있었다(별개 원인, 2026-09-12 부터 미해결).
